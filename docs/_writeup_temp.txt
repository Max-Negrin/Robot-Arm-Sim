OVERVIEW
--------
I built a 3-joint stepper motor robot arm controlled by a Raspberry Pi Pico 2W.
The system implements two independent network interfaces simultaneously:

  1. USB Serial (wired)    -- primary real-time control channel
  2. WiFi HTTP + TCP (wireless) -- browser-accessible dashboard and LAN control

The Pico 2W runs a custom MicroPython firmware (main.py) that manages both
interfaces concurrently: core 0 runs the motor control loop, core 1 runs the
LAN services thread (HTTP :8080 + TCP :8888).

USB SERIAL PROTOCOL
-------------------
The desktop app streams joint angles as ASCII lines at up to 200 Hz:

  T:0.050,J0:45.00,J1:-12.50,J2:30.00   <- timestamped trajectory point
  SYNC J0:0.00,J1:0.00,J2:0.00           <- absolute position sync
  JOG J1 5                                <- relative jog command
  PING                                    <- round-trip latency probe
  HOME                                    <- animate to zero

Pico replies:
  OK
  POS:J0:44.99,J1:-12.48,J2:29.97        <- 1 Hz position stream
  PONG <ms>                               <- latency reply

WiFi TCP :8888
--------------
Accepts the same ASCII line protocol as USB serial. Used by the desktop app
for wireless (cable-free) control at the same update rate as USB. The Pico
parses commands identically regardless of source (USB or TCP).

------------------

  - Driver type    ("stepdir" -- STEP/DIR GPIO, PIO-accelerated)

PIO STEP GENERATION
-------------------
NEMA 17 stepper drivers (A4988/DRV8825) require STEP pulses with >1 us HIGH
time. The original 125 MHz PIO clock produced 64 ns pulses -- invisible to
the driver and averaged to 0V on a multimeter.

Fix: Changed PIO clock to 2 MHz. 8 PIO cycles x 500 ns = 4 us HIGH pulse.

  @asm_pio(set_init=PIO.OUT_LOW)
  def _pio_step_pulse_program():
      pull(block)               # wait for period value from FIFO
      mov(x, osr)               # x = period (countdown)
      label("loop")
      jmp(x_dec, "loop")        # delay = period x 0.5 us
      set(pins, 1) [7]          # HIGH for 8 cycles = 4 us at 2 MHz
      set(pins, 0)              # LOW -- one complete step pulse

The main loop feeds step periods via sm.put(period) at the velocity
determined by axis_plan_velocity_steps().

DEPLOYMENT
----------
The GUI has a one-click Deploy button that:
  1. Reads the current Motor Configuration panel settings
  2. Injects the JOINTS block, WiFi credentials, and HTTP/TCP port numbers
     into the firmware template using sentinel markers:
       # <<BEGIN_JOINTS_CONFIG>> ... # <<END_JOINTS_CONFIG>>
  3. Uploads to the Pico via mpremote or raw serial REPL
  4. The Pico resets and immediately runs the new config

MOTOR CONTROL -- VELOCITY PLANNER
─────────────────────────────────────────────────────────────────────────────

Function: axis_plan_velocity_steps() in firmware/pico_control_script.py

  def axis_plan_velocity_steps(dt, signed_position_error_steps, vel_signed,
                                frac_carry, dv_prev, max_speed_sps,
                                accel_sps2, jerk_sps3, max_burst):

      ae = max(accel_sps2, max_speed_sps * 10.0)
      a  = abs(signed_position_error_steps)

      # Graceful deceleration at target -- no snap-to-zero
      if a < 0.5:
          if abs(vel_signed) < 1.0:
              return 0, 0.0, 0.0, 0.0
          dv = copysign(min(ae * dt, abs(vel_signed)), -vel_signed)
          return 0, vel_signed + dv, frac_carry, dv

      # Stopping-distance velocity cap (trapezoidal profile)
      ds    = max(0.0, a - 0.5)
      v_cap = min(max_speed_sps, sqrt(2.0 * ae * ds))
      v_cmd = copysign(v_cap, signed_position_error_steps)

      # Acceleration limit
      dv_raw = clamp(v_cmd - vel_signed, -ae*dt, ae*dt)

      # Optional jerk limit (S-curve smoothing)
      if jerk_sps3 > 0:
          lim    = jerk_sps3 * dt * dt
          dv_raw = clamp(dv_raw, dv_prev - lim, dv_prev + lim)

      vel_signed += dv_raw
      frac_carry += abs(vel_signed) * dt
      n_steps     = int(frac_carry)
      frac_carry -= n_steps
      return min(n_steps, max_burst), vel_signed, frac_carry, dv_raw

Design decisions:
  - frac_carry accumulates fractional steps across ticks -- no stuttering
  - v_cap = sqrt(2*a*ds) ensures motor stops before target (no overshoot)
  - Jerk limit smooths the acceleration ramp (S-curve profile)
  - At target (a < 0.5 steps), velocity decays at accel rate rather than
    snapping to zero -- eliminates abrupt stop sound/feel

WEB JOG TARGET ACCUMULATION
  Web jog commands accumulate on target_pos (step domain):
    delta_steps = ddeg / 360.0 * axis._steps_out
    axis.target_pos += delta_steps

  This ensures rapid hold-jog pulses build up a leading target even before
  the motor has physically moved. The motor chases the accumulated target
  at its configured accel/jerk profile, producing smooth continuous motion.

PROBLEMS ENCOUNTERED AND SOLUTIONS
─────────────────────────────────────────────────────────────────────────────

PROBLEM 1: 0V on all STEP/DIR pins -- motors not moving
  Symptom:   Multimeter read 0V on STEP pin even while arm should be moving.
  Diagnosis: PIO at 125 MHz produces a 64 ns STEP HIGH pulse. Multimeter
             averages to 0V. A4988 minimum STEP pulse width = 1 us.
  Fix:       Changed PIO clock 125 MHz -> 2 MHz. 4 us HIGH pulse.

PROBLEM 2: STEPT command blocking for 10+ seconds per step
  Symptom:   STEPT 0 200 took extremely long to complete.
  Diagnosis: When host_follow_vel = 0, PIO period = CLOCK / (2 * 0) = inf.
             Clamped to 62.5M cycles = 0.5 s per step x 200 = 100 s total.
  Fix:       Added _PIO_MIN_SPS = 20. Worst case: 50 ms per step.

PROBLEM 3: LIMITS terminal command starting the PINS stream
  Symptom:   Typing LIMITS enabled the GPIO pin debug stream unexpectedly.
  Diagnosis: Two elif handlers matched "LIMITS" -- one for joint limits
             display (correct) and one for pin stream toggle (wrong name).
  Fix:       Renamed pin-stream commands to LIMSWITCH / LIMSWITCH ON / OFF.

PROBLEM 4: Web jog j=0 hardcoded bug
  Symptom:   All web jog buttons jogged joint 0 regardless of which was pressed.
  Diagnosis: JavaScript setInterval closure captured loop variable j by
             reference, not by value. All closures saw the last j value = 0.
  Fix:       Replaced with attachHold(btn, urlFn) helper that closes over
             idx (local const) per button creation.

PROBLEM 5: NameError: _backlash_angle_rad_from_motor_cfg
  Symptom:   Timer tick crashed every 20 ms with NameError in main_window.py.
  Diagnosis: Function defined in panels.py but missing from import list
             in main_window.py.
  Fix:       Added _backlash_angle_rad_from_motor_cfg to the import.

PROBLEM 6: Sudden/immediate deceleration at end of moves
  Symptom:   Motor reached target and stopped with an audible snap.
  Diagnosis: axis_plan_velocity_steps() returned (0, 0, 0, 0) immediately
             when position error < 0.5 steps, regardless of current velocity.
  Fix:       Apply accel-rate deceleration each tick until speed < 1 sps.

PROBLEM 7: Web jog not moving arm despite /api/state reporting angle changes
  Symptom:   Holding jog button incremented dashboard angles but no movement.
  Diagnosis: _apply_web_command read current_pos and set target = current +
             delta. If motor had not moved between two 100 ms jog pulses,
             both mapped to the same target. Target never accumulated.
             Also, clear_host_follow_rates() zeroed velocity after each pulse.
  Fix 1:     Accumulate directly: target_pos += delta_steps
  Fix 2:     Removed clear_host_follow_rates() from web jog handler.

PROBLEM 8: Chunk progress flooding hardware_log.txt
  Symptom:   Every firmware deploy added ~40 INFO lines (one per 5 chunks).
  Fix:       Changed _prog() from logger.info to logger.debug. GUI panel
             still shows all progress via progress_cb. Log only shows INFO+.
